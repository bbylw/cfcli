CI 与本地最大的差别在于：没有人可以回答提示。`cf` 在探测到非交互式环境时会改用默认值，或在必须有明确答案时失败。

## GitHub Actions 示例

下面这个工作流在每次 pull request 与 push 到 `main` 时构建一次：先用 dry run 校验，只在 push 到 `main` 时部署同一份构建产物。

```yaml
name: Deploy

on:
  pull_request:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    env:
      CF_SEND_TELEMETRY: "false"
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npx cf build
      - run: npx cf deploy --prebuilt --mode production --dry-run
      - if: github.event_name == 'push'
        run: npx cf deploy --prebuilt --mode production
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
```

只有最后一步会拿到密钥，因此前面的步骤对来自 fork 的 pull request 也能运行。把 `cf` 装为开发依赖后，`npx cf` 每次都使用项目锁定的那一份。

## 使用 API token

在 CI 中不要运行 `cf auth login`，改为设置：

```sh
export CLOUDFLARE_API_TOKEN=<API_TOKEN>
export CLOUDFLARE_ACCOUNT_ID=<ACCOUNT_ID>
```

`CLOUDFLARE_API_TOKEN` 的优先级高于任何已保存的登录状态，因此它同时也是无人值守智能体的认证方式。只授予任务实际需要的权限。

<Callout variant="warn" title="保管好 token">
  不要把 API token 写入版本库。在 CI 中使用平台的密钥存储，并把 token 注入为环境变量。若使用 `.env` 文件，确认它已被 `.gitignore` 排除。
</Callout>

## 明确告知这是 CI

设置 `CI=true` 可以避免交互式提示，提示会使用默认值，或在必须回答时失败。`cf` 也会自行探测常见 CI 提供方以及终端缺失的情况，但显式设置更可靠：

```sh
export CI=true
```

## 先配置，再进 CI

自动配置在终端中会先展示计划改动并询问；在 CI 中它会直接应用改动并安装依赖。为了让流水线的行为可预测，建议在本地先运行：

```sh
cf init .
```

它会在不构建的前提下配置已有项目。复查改动并提交，之后再让 CI 运行构建命令。

## 分阶段流水线

`cf` 把构建与部署解耦，因此可以先构建一次、在后续阶段复用产物：

```sh
# 构建阶段
cf build

# 部署阶段
cf deploy --prebuilt
```

`--prebuilt` 跳过构建与自动配置，直接部署已有的 Build Output（`.cloudflare/output/v1/`）。`cf build` 不上传任何内容，也不需要凭据。

部署时必须传入 Build Output 记录的同一个 mode。Vite 构建总会记录 mode：`cf build` 不带 `--mode` 时记录 `production`，所以部署也要传 `--mode production`；用 `--mode staging` 构建就用 `--mode staging` 部署。mode 不一致时，部署会在上传前停止并打印应使用的值。

要验证构建而不发送任何 API 请求：

```sh
cf deploy --dry-run
```

## 关闭遥测

在 CI 中如果不希望发送匿名使用遥测：

```sh
export CF_SEND_TELEMETRY=0
```

或用更通用的：

```sh
export DO_NOT_TRACK=1
```

`DO_NOT_TRACK` 的优先级最高，即使 `CF_SEND_TELEMETRY` 已启用也能关闭遥测。

## 输出与日志

结果写入标准输出，进度、消息与错误写入标准错误。因此日志天然分离，可以把标准输出重定向到文件交给后续步骤处理：

```sh
cf zones list > zones.json
```

失败的命令以非零状态退出。在非交互式会话中，不带 `--force` 的破坏性命令会打印 `Aborted.`、不做任何修改，并以状态码 `1` 退出。
